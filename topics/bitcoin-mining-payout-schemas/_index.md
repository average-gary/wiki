# Bitcoin Mining Payout & Accounting Schemas

Survey of how Bitcoin mining pools account for hashrate contributions and pay miners. Centralized variance-smoothing schemes (FPPS, PPS+) versus risk-sharing schemes (PPLNS), versus Stratum-V2-job-declared variants (PPLNS-JD), versus decentralized share-chain accounting (p2pool / p2poolv2), versus ecash-redemption mints (hashpool.dev).

## Top-level questions

1. What are the canonical payout schemas (PPS, PPLNS, FPPS, PPS+, SOLO) and what risks does each one shift to whom?
2. How does Stratum V2 Job Declaration change accounting — what is "PPLNS-JD" and which pools claim to run it?
3. How does hashpool.dev use Cashu ecash mints to redenominate shares as bearer tokens, and what trust assumptions does that introduce?
4. How does p2pool / p2poolv2 do payout via a coinbase-output share-chain — what are PPLNS window semantics in a decentralized chain?
5. What was discussed in the btc++ payout/accounting tracks (Riga, Austin, Salvador) about decentralizing or improving pool accounting?
6. Cross-cutting: how do payout schemes interact with custody (custodial vs non-custodial), variance, fee policy, and SV2 negotiated job submission?
7. Attribution: what does a pool structurally have to know about each miner, how much of that is merely conventional, and can an operator make itself unable to retain it?

- 2026-07-30: **Fifth revision of the xpub-identity spec — a code read moved most of the work pool-side and found a silent 100%-to-pool defect** → [[output/plan-xpub-miner-identity-spec-2026-07-29|technical spec]]. An exhaustive, adversarially-verified multi-agent read of the `sv2-apps-coinbase-rotation` clone at HEAD `e2930150` **retracted fifteen claims** from the previous two revisions. The blocking one: `PayoutMode::try_from` has no descriptor arm and `script_from_address` wraps its input as `addr(<descriptor>)`, so a **valid, untruncated wildcard descriptor** falls through the `/`-split to `NoPayoutMode`, which the pool maps to `PayoutMode::FullDonation` — one output, the entire block value, to the pool's own script, persisted for the connection's lifetime, **no error returned and nothing logged.** Prior revisions had assumed an unrecognized identity would be rejected; it is silently expropriated, so the fail-closed fix is now non-optional Phase 1 work. The structural retraction: the Translator was never the bottleneck. `Downstream.payout_mode` is **one slot per TCP connection**, blind-overwritten on every channel open and never cleared on close, and extended channels inherit the group job which **never rebuilds the coinbase** — so N devices on one connection collapse to the last-opened identity from the next `NewTemplate` onward. Each channel's *first* job **is** built from its own parsed mode, which is why a first-job test passes while production mispays, and there is no regression test for it anywhere (every case in `pool_solo_mining.rs` uses one identity per connection). The Translator work grew from 3 changes to **7**; the pool-side work is **6 more and larger**, and is a prerequisite for any multi-channel connection, which reverses the previous revision's phase ordering. `aggregate_channels = false` turns out to be **structural, not a tuning knob** — `AggregatedState::NoChannel` is the only arm reaching the upstream sender, every channel id collapses to `AGGREGATED_CHANNEL_ID = u32::MAX`, and devices are separated only by a translator-minted 2-byte `local_index`, so per-device identity is *unrepresentable* in that mode however either side is refactored. Two prescriptions **withdrawn**: raising `MAX_USER_IDENTITY_BYTES` is actively harmful (the normative constant lives in external crates; raising the local mirror turns warn-and-truncate into a hard disconnect on the first share) — the route is around it, via the already-untruncated `authorized_worker_name`, with `Str0255`'s 255 bytes as the real limit; and key-origin information must be **stripped** during normalization, because `wpkh([fp/84h/0h/0h]xpub…/0/*)` and `wpkh(xpub…/0/*)` yield different `payout_id`s and **byte-identical** `scriptPubKey`s, which `PRIMARY KEY (block_height, payout_id)` does not catch. Measured rather than estimated: the shortest wildcard forms are `tr` **126** / `pkh` 127 / `wpkh` 128 bytes, closing the open question about fitting under Avalon's 63-char truncation as a negative. Also recorded: this clone is a **solo/donate coinbase-templating pool, not a reward-sharing one** — `coinbase_outputs` maxes at two outputs, share accounting is per-channel monotonic counters with no window, a found block forwards the finding channel's coinbase verbatim, and `grep -i pplns` returns zero hits — so the spec's PPLNS-facing sections rest on the wiki articles alone, not on this code. Nothing was executed; ten residual risks are recorded rather than resolved, the load-bearing one being whether per-channel coinbase templating is confined to this repo or needs an upstream `channels_sv2` change.
- 2026-07-29: **Thesis round on blinded share credit → verdict MIXED** ([[wiki/theses/blinded-share-credit-commitment|thesis]], [[output/report-blinded-share-credit-thesis-2026-07-29|report]]). 8 lenses, per-sub-claim verdicts because one verdict would have hidden the result. **The or-conjunction splits**: weight aggregation genuinely needs a pool-side pseudonym or a miner-carried accumulator (SUPPORTED), but **duplicate arbitration is FALSIFIED** — a keyed share-derived nullifier `nf = PRF_{sk_M}(header_hash)` is a third mechanism, and three independently written implementations already dedup with **no identity term in the key** (SRI's `seen_shares: HashSet<Hash>`, Ocean/DATUM's `datum_stratum_dupes.h` — checked *before* attribution — and p2pool-v2's `HashSet<&BlockHash>`). New concept: [[wiki/concepts/nullifier-vs-pseudonym|Nullifier vs Pseudonym]]. **The larger result is that every cryptographic barrier this topic was carrying against blinded accumulation dissolved on contact with primary sources**, and four of the five had already propagated into two output artifacts: **Canard–Gouget was *inverted*** (the BBA line cites it as the reason issuer and accumulator *must* share one key — Faller et al., IMACC 2021; BBW Def 4.1 shares `sk_I` across all three roles and p.171 removes the TTP trapdoor; the impossible notion is *Perfect* Anonymity, scoped to coin transfer between **users**); **crediting was costed with the spending row** (`Add` is 62/45 ms and 1,745 B, not `Sub16,lin`'s 122/182 ms and ~4 kB — 4.04× overstated, and 7.2 cores at F2Pool scale when batched at SV2's shipped `share_batch_size = 10`); **the 16-bit range limit binds redemption only** (BBW Fig. 4 p.174: `Proof P2 (Add)` carries no range proof, leaving ~201 bits of headroom over the ~50 bits an `8 × D` window needs); and **ROS is ℓ = 9, not ~256**, with ROS-breaks-ACL **retracted by its own authors**. There is also **no theorem making stateful accumulation harder than one-shot issuance** — the "coins must grow" result people reach for is Chaum–Pedersen (EUROCRYPT '92), which scopes to transferability. **What survives is not cryptographic**: interactivity (offline non-interactive BIP32 derivation vs an online 2-party protocol that **cannot be Fiat–Shamir'd away**, since BBW p.166 relies on rewinding to replace the trapdoor) and the **hashrate side channel**, which batching *converts* rather than removes (`interval = b / share_rate`) and which no paper has quantified. Two obstacles upstream of the whole thesis, both new here: Bedrock keys the **vardiff target on identity** (`store(M.uname, K_M, R_M, target)`), so blinding breaks share *validation* before crediting; and Bedrock specifies no duplicate handling at all, so C had no baseline to lose. Standing process hazard recorded: **WebFetch silently fails on image-based PDFs and returns confident "ABSENT" verdicts** — the likely source of fabricated author names now removed from two files.
- 2026-07-29: **Specced the xpub-username pool, then revised it to be stateless** → [[output/plan-xpub-miner-identity-spec-2026-07-29|technical spec]] (12 articles + 4 raw sources + 3 direct code reads, 13 sections). The revision is the substance: **the derivation index is the block height being mined**, so `payout_script = descriptor.at_derivation_index(H)` is a **pure function of `(descriptor, height)`** — the pool stores no index, advances no counter, and persists nothing on the payout path. That deleted the entire derivation-store section, its four correctness requirements, three regtest tests, three monitoring metrics, and the **`next_index` must never be rolled back** hazard, which had made ordinary disaster recovery a privacy regression (restore a stale backup → re-derive already-paid indices → address reuse via the operator's own runbook). It also makes reuse **unrepresentable** rather than merely avoided: no height recurs, so a miner has exactly one derivable address per block — which is why "no finder bonus" is load-bearing rather than incidental (bonus + proportional share would be two rows for one `payout_id`, i.e. two outputs paying one address inside one transaction). The accepted cost is stated rather than hidden: **a bare seed restore finds nothing**, because Sparrow's gap limit is a *depth* past the last used index (20, 40 postmix) and BDK's `DEFAULT_LOOKAHEAD` is 25, so neither reaches ~900,000 by configuration — recovery requires `bitcoin-cli deriveaddresses`/`importdescriptors` with an explicit absolute `range`, and the spec pins that as an executable test asserting the seed restore *does* fail. Two structural corrections to the first draft, both from reading the clone rather than reasoning about it: **V1 miners are not excluded** — they reach the pool through the **SV2 Translator** with the descriptor in `Upstream.user_identity`, which inverts the firmware problem (Avalon's 63-char truncation and Whatsminer's overflow past 127 apply to a config file the operator controls, not an ASIC buffer) at the cost of one shared `payout_id` per Translator upstream; and **`user_identity` already has a `/`-delimited grammar that collides with descriptor syntax** (`sri/solo/<addr>`, `sri/donate/<pct>/<addr>`, plus a `.` split in `address_part_from_user_identity`), survivable only by committing to descriptor-parse-first precedence — which the existing code already happens to have. Upstream framing worth noting: SV2 PR #1720's own rejection comment reads *"gmax thinks it would be cool if we would instantiate it with the blockheight or something, but need to work out UX"* — so the spec implements the deferred parenthetical, and §6 is the UX work that deferred it. **Second revision same day**: the V1 path is **Translator passthrough** — the miner sets its own `mining.authorize` username to the descriptor and the Translator forwards it upstream unmodified, giving per-rig payout identity instead of one identity per Translator. Reading the code showed the current Translator **cannot** do this, for three independent reasons that make it a modification rather than a config recipe: channel `user_identity` comes from an `Arc<OnceLock<String>>` filled from TOML (so today every V1 rig behind a Translator would be paid to the *operator's* descriptor); the upstream channel opens on the **first** downstream message with the V1 handshake queued behind it, so authorize hasn't arrived when identity is chosen; and the one path that does carry the miner's own username is capped at **32 bytes** (`tlv_compatible_username`, warn-and-truncate) and is then **discarded by the pool** (`if let Some(_user_identity) = … { /* …in the future */ }`). Silver lining: a 32-byte cut loses the closing paren and `#checksum`, so it fails the grammar rather than deriving a wrong address — fail-closed, now pinned as a test. This also **withdraws** the previous revision's claim that the Translator "deletes the entire firmware field-width problem class" — true only for operator-set identity; under passthrough the descriptor is typed into the rig, so Avalon's 63-char truncation and Whatsminer's overflow bind again, and both paths are now presented as an explicit operator tradeoff (farm-wide identity that works on any firmware today, versus per-rig identity needing ~150 chars of username). One existing exemption shows the way: the code already skips the `.miner{N}` suffix for `sri/`-prefixed identities (*"appending a suffix would break pool-side validation"*, issue #369) and descriptors need the same. Also **closed §9.5**: the spec still called Bedrock's mining-cookie question "unanalyzed by anyone" citing an active inventory record, but the thesis round below resolved it and `blinded-mining-cookie-security` is `resolved: 2026-07-29`. The resolution favours this design — it keeps identity in the clear, so identity-keyed vardiff, dedup, and crediting are untouched — and the thesis's one surviving obstacle (crediting is an online interactive protocol, payout an offline non-interactive derivation) is precisely the argument that this plan takes the tractable half.
- 2026-07-29: **Attribution-privacy round** — 10 sources compiled into 8 new articles ([[wiki/topics/self-blinding-pool-design-space|Self-Blinding Pool Design Space]], [[wiki/concepts/payout-attribution-privacy|Payout Attribution Privacy]], [[wiki/concepts/hashrate-inference-side-channels|Hashrate Inference Side Channels]], [[wiki/concepts/coinbase-amount-linkability|Coinbase Amount Linkability]], [[wiki/concepts/blind-share-accounting|Blind Share Accounting]], [[wiki/concepts/xpub-payout-identity|Xpub Payout Identity]], [[wiki/concepts/self-blinding-architectures|Self-Blinding Architectures]], [[wiki/decisions/attribution-retention-tradeoffs|Attribution Retention Tradeoffs]]) + a [[output/playbook-self-blinding-pool-attribution-2026-07-29|playbook]]. The load-bearing finding **reorders the question**: a pool's attribution knowledge comes from share *validation*, not from *payment*, so a miner-supplied xpub and any payout blinding defeat only chain observers (Romiti et al. identified 92 %/75 %/30 % of individual miners at BTC.com/ViaBTC/AntPool from public data alone) while leaving the pool's own knowledge untouched. Two structural impossibilities recorded: **BIP 352 silent payments cannot work in a coinbase** (no input private key → `a = 0` → fail, from the BIP's own algorithm), and a coinbase is a **strictly easier subset-sum instance than a CoinJoin** (one input of publicly known value, no input shuffling, no padding because the total is consensus-bound). BBA+/Black-Box Wallets is the only primitive that natively accumulates quantitative weight, ~~blocked for a single-operator pool by Canard–Gouget~~ — **corrected by the 2026-07-29 thesis round below: the single-operator case is the one BBA+ and BBW prove secure, and Canard–Gouget is cited in that literature for the *opposite* proposition.** Three objections survive: share-credit theft (the cryptographic crux — cf. the Bedrock mining cookie `C_M = H²(R_M, M.uname)`, ~~whose blinded variant nobody has analyzed~~ → now verdicted, see below), the dust→accrual→custody→money-transmitter chain (FinCEN §4.5.1(a) makes an anonymizing transmitter expressly ineligible), and compulsion, which only blocks *future-tense* promises. Withholding detection is **not** among them — the withholding literature shows attribution-based detection already fails under full identity, with Eligius 2014 address clustering the one exception, and that cost belongs to address *rotation*, not blinding. Also qualified [[wiki/concepts/ehash|eHash]]'s flat unlinkability claim against hashpool's own docs (denomination leak `amount MUST equal 2^(share difficulty − keyset minimum difficulty)`, retained `header_hash`, cleartext `payout_address` in `SETTLEMENT_DESIGN.md`) with an in-article correction notice.
